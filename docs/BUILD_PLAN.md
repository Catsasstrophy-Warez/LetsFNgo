# Nexus — Build Plan (pre-code deliverables A–E + Intelligence layer)

Status: draft for review · 2026-09-27
Inputs: `docs/handoff/*` (Nexus AI Handoff) and the `septtechtrainer` Swift package (Controls Technician Trainer & Simulator).

This document answers the handoff's required pre-coding deliverables (A–E) and adds
section F. Section F covers the local, layered LLM and full Apple Intelligence integration
that was added as a requirement after the handoff was written. Nothing here weakens a
locked decision. Where a decision is extended, the extension is called out.

---

## 0. What we are starting from

### Nexus handoff
This is a specification only; it contains no code. The locked model is
`Project → Object → Relationship → Event → Evidence → Action`. The rules that carry the most weight are:
- seven truth classes that must never be silently collapsed
- provenance on every meaningful value
- SQLite and FTS5 as the canonical store
- agents with P0–P5 permissions
- one simulation clock
- ObjectID-mapped RealityKit
- the Golden Vertical Slice (diagnose an instrument-loop failure end to end) before any domain fan-out

### septtechtrainer
This is working code: about 40k lines of Swift 6.2 in three targets (`Core` → `Simulation` → `UI`), with about 550 tests.
Verified 2026-09-27 on Linux with Swift 6.2: `swift test` passes all **554 tests** (299 XCTest + 255 Swift Testing). SwiftUI sources are skipped on Linux via `canImport`.

It is the most mature engineering asset we have, and it already embodies much of what Nexus needs in the Engineering, Investigation and Learning areas:

| Nexus concept | Trainer equivalent (today) |
|---|---|
| Deterministic simulation | `PLCEngine`, `ControllerRuntime` (scan, prescan, first-scan, forces, faults) |
| Truth layers | `FlightSignalLayer` (field / controllerInput / logic / output), physical vs PLC-observed snapshots, `EvidenceKind {fact, measurement, assumption, inference}` |
| Investigation engine | `CausalJournal.explainWhy`, `MultiHypothesisReport`, `AdaptiveTroubleshootingSession`, `EvidenceConfidence`, contradiction detection |
| Discriminating next test | `DiagnosticStrategy` (information gain vs effort/safety/access) |
| First divergence | `SequenceReconstruction` (earliest meaningful divergence vs reference) |
| Measurement | `VirtualMeter`, `MeasurementProfile`, `CalibrationAnalyzer` |
| Instrument loop | `CurrentLoopModel` (4–20 mA compliance/headroom), `MachineFieldFaultKind` (open wire, drift, failed low/high…), `SampledDataPID` |
| Training scenario | Scenario packs, campaigns, certification, spaced mastery |

Known gaps in the trainer, all of which the plan addresses:
1. The reasoning logic lives in the UI target, so it cannot be used headlessly.
2. There is no shared clock or world-state protocol; about 20 standalone `Runtime`/`Snapshot` pairs each define their own.
3. There are several parallel hypothesis/evidence models and several physical-vs-observed models.
4. Persistence is UserDefaults JSON with swallowed errors.
5. There is no single "instrument loop" entity; `CurrentLoopModel` is only used by tests.
6. Dense `;`-joined code-golf lines in several files.
7. The app is iOS-only.

**Decision: absorb, don't fork.** The trainer becomes Nexus's engineering and learning engine. We port it into the monorepo incrementally, target by target, behind Nexus protocols. It does not stay a sibling app with its own truth store; that would violate locked decision #1.

Rules:
- Every Apple-only framework (SwiftUI, RealityKit, FoundationModels, AppIntents, CoreSpotlight) is used only inside `#if canImport(...)`, and only in targets explicitly marked Apple-only. Everything else must build and test on Linux, which is how CI and cloud sessions validate it.
- Domain modules may not own a canonical store. They read and write through `NexusPersistence` / `NexusGraph`.
- Later domains (Finance, Automotive, Creative…) get their targets only after the Golden Slice passes.

## B. Canonical schemas

Swift, abbreviated. All types are `Codable`, `Sendable` and `Hashable`.

```swift
struct ObjectID: Hashable, Codable, Sendable { let raw: UUID }   // UUIDv7 for time-sortable ids
enum TruthClass: String, Codable { case recorded, observed, modeled, claimed, derived, display, agentInterpretation }

struct Provenance: Codable {
  var origin: Origin            // .user(id) | .agent(id, runID) | .import(sourceID) | .simulation(runID) | .instrument(id) | .model(ModelRef)
  var truth: TruthClass
  var timestamp: Date
  var method: String?
  var confidence: Double?       // 0…1, nil = not assessed
  var dependencies: [ObjectID]  // inputs this value was derived from
  var transformation: String?
  var revision: RevisionID
}

struct ObjectRecord { id, type: ObjectType, title, attributes: [String: Value], lifecycle, createdAt, provenance }
struct Relationship { id, kind: RelationKind, from: ObjectID, to: ObjectID, validFrom/validTo, confidence, provenance }
struct Event { id, at: Date, kind, subjects: [ObjectID], payload, provenance }
struct Claim { id, statement, sources: [ObjectID], passages, sourceClass, applicability, confidence, counterevidence: [ObjectID] }
struct Measurement { id, quantity, value, unit, uncertainty, resolution, range, testPoint: ObjectID, instrument: ObjectID?, loading, sampledAt, truth /* observed|modeled|display */ }
struct Hypothesis { id, investigation, statement, state: candidate|confirmed|rejected|unknown, supports, contradicts, requiredObservations, discriminatingTests, safetyConstraints }
struct AgentRun { id, agent, goal, plan, steps: [AgentStep], permissionsUsed, outputs: [ObjectID], errors, approvals, model: ModelRef, usage }
struct Revision { id, object, parent, author: Origin, instruction: String?, diff, at }
struct ModelRef { provider, modelID, adapterID?, adapterVersion?, promptHash }   // §F provenance for AI output
```

SQLite layout:
- `objects(id PK, type, title, attrs JSON, lifecycle, created_at, prov JSON)`
- `relationships(id, kind, from_id, to_id, valid_from, valid_to, confidence, prov)`, indexed on `(from_id, kind)` and `(to_id, kind)`
- `events(id, at, kind, payload, prov)` and `event_subjects(event_id, object_id)`
- `revisions`
- `claims`
- `measurements`
- `agent_runs` and `agent_steps`
- `blobs(id, sha256, uri, mime)`
- `objects_fts` (FTS5, content-linked)
- `schema_migrations`

Values carry their truth class and provenance as columns, so no reader can lose them.

## D. Golden Vertical Slice acceptance plan

**Scenario.** Tank level loop LT-101 → AI card → PID → level valve. The fault is a high-resistance terminal that causes loss of transmitter compliance at high current, so the reading clamps and drifts only near the top of the range. This is a good test because it is intermittent, it is range-dependent, and display truth diverges from process truth.

The steps map onto the 14 acceptance tests in `docs/handoff/ACCEPTANCE_TESTS.md`:

1. Create the project, then the loop topology: transmitter, wiring and terminals, barrier, AI channel, PID, valve. Every item is an Object and every connection a Relationship.
2. Attach the transmitter manual PDF and create a claim ("minimum lift-off 12 V"), cited to the manual and classed as primary.
3. Open the same object from Project, Search, 3D and Investigation. Its `ObjectID` must be identical in every view.
4. Inject the fault into `NexusSimulation`. The solver is `CurrentLoopModel`, promoted and wired to the clock.
5. Record a DMM reading at TB-4 (**observed**) next to the simulated node voltage (**modeled**) and the HMI value (**display**). All three are stored, and none overwrites another.
6. Hypotheses:
   - H1: transmitter failed
   - H2: loop resistance or compliance
   - H3: AI card
   - H4: scaling
7. `DiagnosticStrategy` picks the discriminating test, a loop-voltage-under-load measurement at the transmitter terminals.
8. Mark the first divergence, where the loop voltage at the transmitter terminals drops below lift-off.
9. Create a repair procedure and a task.
10. Verify with a post-repair sweep from 4 to 20 mA.
11. Generate a report. Every figure in it links back to its measurement or claim.
12. Generate a training scenario, a `NexusLearning` scenario seeded from this case.
13. Save the knowledge.
14. Kill the process, reload, and diff the graph, events, claims, measurements, revisions and timeline. The diff must be empty.

Every step is a headless integration test that runs on Linux CI. UI and RealityKit steps get Xcode UI tests on top.

## E. Risks and migration strategy

| Risk | Mitigation |
|---|---|
| Scope: 36 domains | Hard gate: no domain target is added until the Golden Slice test passes. |
| Porting 40k lines of trainer code while restructuring it | Port in layers, one at a time: PLC (verbatim), then reasoning (moved out of UI, API unchanged), then physics (adapted to the solver protocol). The trainer's own tests come along at each step and must stay green. |
| Several hypothesis and evidence models in the trainer | Unify them on `NexusInvestigation.Hypothesis` and `Measurement`. The trainer types become adapters, and the adapters are deleted once their call sites migrate. |
| UserDefaults persistence in the trainer | Replaced by `NexusPersistence`. We write a one-time importer for `…LearningState.v1` so no learner progress is lost. |
| Apple-only frameworks can't be tested in a Linux cloud session | Keep a strict `canImport` split. The core stays Linux-testable, and the Apple layers get a macOS Xcode CI lane (GitHub macOS runner). |
| On-device model limits (context window, quality, locale, device eligibility) | Route through `NexusAI` with fallbacks (§F), and apply the same deterministic tools regardless of model. |
| LoRA adapters are tied to a base-model version | Keep a versioned adapter registry, plus a retrain-and-eval pipeline triggered by each OS model update. Fall back to base model + tools when no adapter matches. |
| AI output treated as truth | All model output is tagged `agentInterpretation`, with a `ModelRef` in its provenance. It can only become a higher truth class through explicit user or instrument confirmation. |
| Schema churn | Versioned migrations from day one, each with a round-trip test. |

## F. Intelligence layer: local LLM, layered, plus full Apple Intelligence

**Direction (chosen): "Both, layered."** Apple's system model and our own fine-tuned open-weights model sit behind one abstraction, and each task is routed to the model that suits it. Everything runs locally by default.

> Verify against Apple's current docs before implementation. WWDC26 reports indicate that in iOS/macOS 27 the Foundation Models framework:
> - has a rebuilt on-device model with better tool calling
> - accepts multimodal (image) prompts
> - has built-in Vision OCR, barcode and Spotlight search tools
> - adds "Dynamic Profiles"
> - supports custom LoRA adapters
> - exposes a `LanguageModel` protocol that non-Apple models can conform to, spanning on-device, Private Cloud Compute and third-party providers
>
> If the `LanguageModel` protocol claim holds, our MLX model can plug in *as* a Foundation Models provider, and much of the routing below becomes configuration.

### F1. Model stack (all behind `NexusAI.LanguageModelProvider`)
| Tier | Model | Where | Used for |
|---|---|---|---|
| L0 | Deterministic engines (PLC, solvers, `DiagnosticStrategy`) | everywhere | Ground truth for engineering answers. LLMs *explain* these results; they never replace them. |
| L1 | Apple on-device Foundation Model + **Nexus domain LoRA adapter** | iPhone/iPad/Mac | Default: guided generation into our schemas (`@Generable` Hypothesis, Claim, Task…), tool calling over the world model, summaries, extraction |
| L2 | **Nexus-tuned open-weights model** via MLX Swift | Mac, M-series iPad | Longer context, deeper diagnostic reasoning, report drafting, offline research synthesis |
| L3 | Apple Private Cloud Compute | opt-in | Tasks too big for local models, with privacy preserved |
| L4 | Third-party cloud (e.g. Claude) | opt-in, **P4 External Action** | Only by explicit per-project policy |

Routing inputs are:
- task type
- required context size
- device capability
- battery/thermal state
- privacy policy of the project and objects involved
- the user's permission policy

### F2. How the models touch the world model
- **Tools, not prompt dumps.** The model gets the following tools:
  - `searchObjects`
  - `getObject`
  - `traverse(relationships)`
  - `getMeasurements`
  - `runDiagnosticStrategy`
  - `explainWhy` (CausalJournal)
  - `runSimulation`
  - `proposeHypothesis`
  - `draftTask`
- Every tool call passes through `NexusPermissions` (P0–P5) and is recorded as an `AgentStep`.
- **Structured output only for writes.** The model proposes typed objects through guided generation. The agent runtime validates each proposal, stores it as a *draft* (P2), and tags it `agentInterpretation`.
- **Retrieval.** We use FTS5 plus graph traversal, and also donate objects to Spotlight so the Foundation Models Spotlight tool can reach them. Semantic vectors remain a modular add-on.

### F3. Training our models ("generate an LLM based on all of this")
The trainer is a **ground-truth data factory**. Its deterministic simulations know the true root cause, the correct causal chain, and the optimal next measurement. That makes them an unusually good source of synthetic supervision.

1. **Dataset generation.** Swift, headless: `Training/DatasetGen` runs thousands of seeded scenarios, covering fault kinds × machines × operating points. It emits:
   - observation-to-hypothesis pairs
   - the next best measurement with its rationale
   - `explainWhy` trails rendered as explanations
   - tool-call transcripts
   - curriculum Q&A drawn from the 23 lessons and the reference library
   - Nexus spec knowledge
2. **L1 adapter.** Train with Apple's Foundation Models adapter toolkit (Python, on a Mac with Apple silicon). Output is a versioned `.fmadapter` shipped as background assets.
3. **L2 model.** Take an open-weights base in the 3–14B class (license checked for commercial use), fine-tune with `mlx-lm` LoRA, merge, quantize to 4-bit, and serve through MLX Swift.
4. **Evals, gated in CI.** Use held-out scenarios with known answers. Metrics:
   - root-cause accuracy
   - next-test optimality versus `DiagnosticStrategy`
   - tool-call validity
   - hallucinated-value rate: any number not traceable to a tool result counts as a failure
   - truth-class discipline

   A model version ships only if it beats the previous version on every metric.
5. We do **not** pretrain from scratch.

### F4. Apple Intelligence surface area ("in every way possible")
| Apple capability | Nexus use |
|---|---|
| **App Intents + App Entities** | Every canonical object type is an `AppEntity` keyed by `ObjectID`. Intents cover Open, Ask, Measure, Start Investigation, Run Simulation and Create Task. This powers Siri, Shortcuts, Spotlight actions, the Action button and Control Center controls. |
| **Siri with personal context and on-screen awareness** | Entities and intents let Siri act on "this transmitter" that is on screen. |
| **Spotlight (CoreSpotlight + semantic index)** | Donate objects, claims and procedures. This also feeds the FM Spotlight retrieval tool. |
| **Visual Intelligence** | Point the camera at a nameplate or tag, match it to an equipment object, and open it. Combine with FM Vision/OCR tools to read nameplates and meters. |
| **Writing Tools** | Available in all Nexus text surfaces: reports, procedures, notes. |
| **Image Playground / Genmoji / Image Wand** | Creative workspace, and illustrations for training scenarios. |
| **Speech (SpeechAnalyzer) + FM summarization** | Meetings and field voice notes become structured decisions, tasks and claims. |
| **Translation framework** | Multilingual procedures and sources. |
| **Vision / Live Text** | Documents, schematics OCR, meter readings. |
| **Live Activities / Widgets / Controls** | Long agent runs, running simulations, the active investigation. |
| **Foundation Models** | L1 above: guided generation, tools, adapters, multimodal prompts, Dynamic Profiles. |

All of this lives in `NexusAppleIntelligence` behind `canImport`, and it is a *view and adapter* over the canonical model. The same permission and provenance rules apply.
